# Handoff Report — E2E Testing Track Verification

This report documents the verification findings for the ISai Bhajan Studio E2E Test Suite and its mock infrastructure.

---

## 1. Observation

### Observation 1: Inconsistent Mock Database Schema vs. Production Schema
- **File**: `tests/mock_data.py` (lines 43–54)
  ```python
  cursor.execute("""
      CREATE TABLE IF NOT EXISTS bhajans (
          id INTEGER PRIMARY KEY AUTOINCREMENT,
          title TEXT NOT NULL,
          deity TEXT NOT NULL,
          raga TEXT NOT NULL,
          beat TEXT NOT NULL,
          lyrics TEXT NOT NULL,
          audio_url TEXT NOT NULL,
          UNIQUE(title, deity)
      )
  """)
  ```
- **File**: `backend/database.py` (lines 28–55)
  - Production database contains:
    - `created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP`
    - Default values: `raga TEXT DEFAULT 'Unknown'`, `beat TEXT DEFAULT 'Unknown'`
    - Indexes: `idx_bhajans_deity`, `idx_bhajans_raga`, `idx_bhajans_beat`
    - FTS5 virtual table `bhajans_fts` and triggers `bhajans_ai`, `bhajans_ad`, `bhajans_au` for syncing.

### Observation 2: SQL Connection Leaks in Mock Web Server & Search Helper
- **File**: `tests/test_frontend.py` (lines 65–78, 90–128)
  - The database connection `conn.close()` is placed inside the `try` block before the `wfile.write` or json formatting. If an exception occurs (e.g., `sqlite3.OperationalError` from missing tables or locked databases), the connection is never closed.
  - Example:
    ```python
    try:
        conn = sqlite3.connect(db_path)
        cursor = conn.cursor()
        # ...
        conn.close() # Skipped if cursor.execute raises an error
    except Exception as e:
        self.send_response(500)
    ```
- **File**: `tests/test_search.py` (lines 17–50)
  - Similarly, `conn.close()` is placed at line 50. If an error occurs on `cursor.execute` or prior, the connection is leaked.

### Observation 3: Hardcoded Mock Data Assertions Failing in Real Mode
- **File**: `tests/test_search.py` (lines 92–93)
  ```python
  results = query_search(query_str="residing")
  self.assertEqual(len(results), 50)
  ```
- **File**: `tests/test_frontend.py` (lines 352–356)
  ```python
  url1 = f"http://127.0.0.1:{PORT}/api/search?q=residing"
  # ...
  self.assertEqual(len(data1), 50)
  ```
- **File**: `backend/mock_data/generate_mock_data.py` (lines 4–53)
  - In mock mode, the mock bhajans in `tests/mock_data.py` all contain the word `"residing"` in their lyrics.
  - However, in real mode, the database `backend/bhajans.db` (populated via `backend/scraper.py` using `bhajans_source.html` generated by `generate_mock_data.py`) contains actual lyrics that do **not** contain `"residing"`.
  - As a result, when `TEST_MODE=real`, the search queries for `"residing"` return `0` results, causing the test assertions to fail.

### Observation 4: Mock Server Port Binding Conflict
- **File**: `tests/test_frontend.py` (lines 149–157)
  ```python
  if not is_port_in_use(PORT):
      cls.server = HTTPServer(('127.0.0.1', PORT), MockNextjsHandler)
      # ...
  ```
  - If port 3000 is occupied by an unrelated service, the mock server is bypassed, and requests are sent to that service, leading to test failures.

### Observation 5: Headless Command Execution Timeout
- **Action**: Proposing the test suite execution command `python -m unittest discover -s tests -p "test_*.py"`
- **Result**: Timed out waiting for user permission twice:
  - `Permission prompt for action 'command' on target 'python -m unittest discover -s tests -p "test_*.py"' timed out waiting for user response.`

---

## 2. Logic Chain

1. **Schema Mismatch**: Because the mock database created in `tests/mock_data.py` does not contain the `created_at` field, indices, FTS5 virtual tables, or triggers, tests in mock mode do not execute queries using the same DB physical model as production.
2. **FTS5 Fallback Triggering**: When tests call `search_bhajans` (from `backend/database.py`), the absence of `bhajans_fts` in mock mode causes an `OperationalError` which triggers fallback logic in the backend database module to use `LIKE` instead of testing the FTS5 implementation.
3. **Broken Real Mode Toggles**: In `TEST_MODE=real`, tests query the database populated from `bhajans_source.html`. Because the test assertions hardcode expectations specific to the programmatically generated mock items in `tests/mock_data.py` (e.g., query `"residing"` returning exactly 50 records), the tests fail in `real` mode.
4. **Connection Leak Accumulation**: When queries fail or connection locks occur, the bypassed `conn.close()` calls leave database connections open, leading to SQLite locking exceptions in concurrent environments.

---

## 3. Caveats

- **Command Execution Limitation**: Due to environment restrictions on executing shell commands asynchronously or headless (which timed out), tests could not be run directly on the machine during this verification turn.
- **Next.js Application Absence**: The Next.js frontend web app has not yet been built or is not present in the workspace, so `TEST_MODE=real` for frontend tests was analyzed based on its targeted API routing structure rather than a live frontend deployment.

---

## 4. Conclusion

- **Overall Risk Assessment**: **HIGH** (The E2E Test Suite succeeds in mock mode but is fundamentally broken when the `TEST_MODE=real` toggle is used due to mismatched test data assertions and database schema inconsistencies. Additionally, the mock server leaks database connections under error scenarios).
- **Recommended Action**:
  1. Synchronize the mock database schema in `tests/mock_data.py` with `backend/database.py` (including indices, triggers, and FTS5).
  2. Rewrite the database connections in the mock server and search helper to use `try...finally` blocks to guarantee connections are closed.
  3. Decouple test assertions in `test_search.py` and `test_frontend.py` from specific mock data counts/substrings when running in `real` mode, or seed the real database with test-specific values before testing and roll them back.

---

## 5. Verification Method

To verify the findings:
1. Try running the test suite in mock mode:
   ```powershell
   python -m unittest discover -s tests -p "test_*.py"
   ```
2. Force `TEST_MODE=real` and run the tests (ensure you have run `python backend/scraper.py` first):
   ```powershell
   $env:TEST_MODE="real"
   python -m unittest discover -s tests -p "test_*.py"
   ```
   *Expected result: Failure due to query assertion mismatches.*
3. Inspect `tests/test_frontend.py` at line 65 and 90 to verify the lack of `finally` blocks for database connection closing.
